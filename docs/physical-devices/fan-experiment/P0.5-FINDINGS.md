## F1. What the model was sent, and why it answered with `snapshot` and `request_cooling_mode`

Evidence. The exact frame is stored in the Tamoz checkpoints (`tamoz.db`, `tamoz_checkpoints` sequence 3 for B, state key `frame`; digest
`sha256:86ae2c6c...`). Call 1 sent only these two messages (input tokens 384, so there is nothing else in the request):

- system = spec `prompt` + `OBJECTIVE: <spec objective>` + a `DIAGNOSIS CODES` list (the three codes of the spec catalog) + one `EVIDENCE:` line + the line
  `OUTPUT: strict JSON object matching the tamoz.episode-diagnosis/v2 protocol; no prose around it.`
  (built by `tamoz/gems/tamoz-agent-kernel/lib/tamoz/agent/episode_frame_builder.rb:118-134`; the TOOLS block of lines 26-34 is added only when the episode has a tool surface, and here `tool_surface` was empty).
- user = `{"situation":[{"id":"fact:facts.temp_mean","value":31.96}, ...]}` (six facts, `episode_frame_builder.rb:146-163`).
- Call 2 is the same system text, and the user JSON gains `"repair_directive":"reasoning_document/unknown_key: top_level.snapshot"` (checkpoint 8, `episode_nodes.rb:388-393`, repair exactly once). The repair carries the error code only, no reminder of the shape.

What the frame does not say anywhere: the key names (`primary_hypothesis`, `diagnosis_probabilities` as an ARRAY of `{diagnosis_code, probability}`, `evidence_refs`,
`recommended_intents` as `[{type, parameter_preset | parameters}]`), that unknown keys are rejected (`reasoning_document.rb:45-51,81,155,195`), and the allowed intent types.
The allowed intent types (`install_watch_condition`, `set_indicator`, `select_thermal_mode`) and their schemas ARE in the wire (`wire.intent_catalog_json`, `episode.allowed_intent_types`) but no frame code puts them into the prompt
(`grep intent_catalog gems/*/lib` finds only validation and digest code). The only schema-like text the model has is the protocol NAME. Tamoz sends `response_format: {"type":"json_object"}` and `temperature: 0`
(`episode_model_transport.rb:34-38`): JSON mode guarantees parseable JSON, never the shape. There is no JSON-schema or tool-call structured output on this path (the conversation path with native tools is separate, line 47).

The three responses (decoded from `tamoz_effect_attempts.result`):

| Call | Top-level keys | Why Tamoz refused it |
|---|---|---|
| A, attempt 1 | `protocol, diagnosis_probabilities` (object), `decision{type: cooling_mode_request}`, `evidence` | first unknown key `top_level.decision` (I ran `ReasoningDocument.parse` on the text to confirm the key order) |
| B, call 1 | `protocol, snapshot{...}, diagnosis_probabilities` (object), `decision{needs_active_cooling, cooling_mode_request{mode: cooling}}`, `rationale`, `evidence` | `unknown_key: top_level.snapshot` |
| B, call 2 (repair) | no `protocol`, `diagnosis_probabilities` (object), `decision{type: request_cooling_mode, mode: active_cooling}`, `evidence` | `unknown_key: top_level.decision` (reproduced offline; the persisted terminal error only says `graph_status: failed`) |

Why those words. The model has only the spec prose, so it paraphrased it. The objective says "You may request a bounded cooling MODE" and the prompt says "a typed decision with a bounded cooling-mode request or a discount of an ambient-tracking rise".
`cooling_mode_request`, `request_cooling_mode`, `bounded`, `duty: null`, `duration: null` and the `ambient_tracking_rise_discount` key are all lifted from that wording. `snapshot` is the model echoing "the immutable snapshot" it was told to analyse.
The reasoning content itself is right and cites the right facts (over_temperature 0.9 to 0.94, ambient discount rejected, no tach credit).

The instruction text comes from Agentic Stream's spec (`cognition.executor.prompt` and `objective`, in `examples/real-world-sensor/zone-thermal-sim.situation.yaml`, passed through unchanged in the wire: `prompt_sha256` matches).
Tamoz's builder adds only the one-line OUTPUT sentence. The September spec has the same prompt and objective byte for byte (`round-007-simulator-pass2/artifact/spec.canonical.json`), so the prose was never read by a model before: the scripted stand-in did not look at it.

Class. Two things together, neither a regression: (a) spec prompt weakness (Agentic Stream config) and (b) a Tamoz frame weakness (it names a protocol but never defines it). The model outcome is a consequence, not the cause.
Recommended action. See F2 and F6. Owner decision needed: yes for the Tamoz side (F2); no for the spec side.

## F2. Classification, and comparison with Tamoz's own thermal fixture

Tamoz's fixture `test/fixtures/domains/thermal-lab.json` (`prompt` field) spells everything out: the line "OUTPUT STRICT JSON with EXACTLY this shape and no other text", the full example object
(`protocol`, `primary_hypothesis`, `diagnosis_probabilities: [{"diagnosis_code","probability"}]`, `evidence_refs: ["fact:<id>"]`, `recommended_intents: [{"type","parameters"}]`), the rules (cover every code once, sum to 1,
at most one intent, no markdown fences), and an `ALLOWED ACTIONS (recommended_intents.type must be EXACTLY one of these ...)` list with the risk of each. Its parameter rule names the field and values for `set_indicator` (`state`: off, watch, alert).
The Tamoz plan says to "reuse cold-chain's strict-JSON output contract" in each domain prompt (`docs/real-world-sensor-tamoz/PLAN.md:92-97`), i.e. the convention is that the DOMAIN prompt carries the contract, and the frame builder does not.
Nothing tells an Agentic Stream spec author this: `documentation/` in Agentic Stream has no text on the output contract, and the checked-in example prompts are two sentences of task description.

Verdict: spec prompt weakness (Agentic Stream config, example spec) plus an undocumented convention (Tamoz frame). This is NOT only a model outcome: three of three responses fail, with three different shapes, which is what a model guessing a schema looks like, and
the model does the reasoning correctly. It is also not provably the model's fault until the shape is given once.
Recommended action: put the contract in the spec prompt for the re-run (F6, config only). Record for the owner: Tamoz should append the protocol definition and the allowed intent types to the system text itself
(then every spec author gets it, and `intent_catalog_json` is not carried for nothing), and the repair message should include the shape and the allowed types, not only the error code.
That is Tamoz code, so record it, do not fix it now.
Owner decision needed: yes (Tamoz change: frame appends output contract and allowed intents; repair repeats them). Optional: json_schema response_format for providers that support it.

## F3. `checkpoint_conflict`: attempt 2 collided with the still-running attempt 1

Evidence (run A).
- Agentic Stream bounds an attempt with `context.WithTimeout(ctx, wallTime)` and puts the same instant into the wire request as `deadline` (`internal/executor/remote/internal/app/executor.go:88-90,120-122` at 91c2079d).
  At the deadline the gRPC call is cancelled and the executor returns at once; it does not wait for the worker's stream to end.
- The attempt is recorded `timed_out`, and `retryOrConcludeFailedEpisode` keeps the episode for another attempt when fewer than three attempts failed (`runner_failure.go:78-99`, `domain/lifecycle.go:31`). There is no delay: attempt 2 (fence 2) was dispatched 7 ms after the timeout.
- Tamoz keys its durable thread by episode only, `thread_id = "episode.<episode_id>"`, namespace `[tenant]`, and only the request id carries attempt and fence (`tamoz-stream/lib/tamoz/stream/situation_request.rb:135-145`).
  The checkpoint writer needs the exclusive lease on that thread; attempt 1 still held it (it was inside the blocking HTTP call to the model until +31.7 s), so the lease acquisition raised
  `CheckpointConflictError "thread namespace already has an unexpired lease"` (`tamoz-sqlite/lib/tamoz/sqlite/lease_operations.rb:46-49`, category `checkpoint_conflict`, `RETRYABLE = true` in `tamoz-core/lib/tamoz/error.rb:137-141`).
- The worker answered with a `FAILED` terminal, reason `checkpoint_conflict` (`stream.db` fence 2 row). Agentic Stream treats a worker-returned terminal as a usable outcome and concludes the episode with it (`runner_conclude.go:17-34,96-120`): no third attempt, although two of three attempts were spent.
  `tamoz.db` afterwards: attempt 1 request stays `running`, attempt 2 request stays `queued`, forever (the worker was stopped by hand).
- Tamoz's cancel is cooperative: `watch_cancellation` (`situation_request.rb:937-949`) flips a token every 100 ms, but a blocking `Net::HTTP` read is not interrupted by it. After the model returned no further checkpoint was written (sequence 3 was the last).

Who is wrong. The worker protocol (`documentation/contracts/worker-protocol.md`, `guides/build-a-go-worker.md`: "Treat cancellation as terminal") does not say the runtime must wait for the worker to confirm that a cancelled attempt ended before it
redispatches, nor that a worker must accept a higher fence while a lower one is still draining. `documentation/learn/runtime-boundaries.md` says a fence rejects stale OUTPUT and "does not cancel an already accepted provider effect". So the contract has a gap, and each side
filled it differently: Agentic Stream redispatches immediately; Tamoz takes an exclusive per-episode lease and fails the newcomer instead of waiting or superseding the old owner. Tamoz's own comment at `situation_request.rb:617` (a concurrent fence+1 redispatch) shows it expected fence+1 redispatch, but not an overlapping one.
Neither side is wrong against its own docs; the combination is wrong.

Regression? No. It is a latent defect: the September stand-in answered instantly, so a deadline never fired and no attempt overlapped. Any model slower than `wallTime` triggers it.
Class: Agentic Stream or Tamoz (latent defect found by this run, not a regression). Action: record; avoid by config (F5). Owner decision needed: yes (which side fixes: a wait or backoff before redispatch in Agentic Stream, a retry-after on the lease in Tamoz, or an explicit protocol rule; a `FAILED` terminal with a retryable reason arguably should count as a retryable attempt).

## F4. `export-run` / `verify-run` say `pass` with zero decisions and zero commands

Evidence. `artifact/verdict.json` is `{"failure_reasons":[],"verdict":"pass"}` for run B, whose episode `concluded` as failed with 0 decisions, 0 commands, 0 intents (`stream.db`).
The verdict is a safety verdict by construction: `internal/runartifact/internal/domain/soak.go:50-108` fails only on six zero-tolerance counters (unsafe output, stale energizing effect, duplicate energizing effect, unexplained actuator transition,
false verified success, safe-state deadline miss), unresolved action outcomes and open reconciliation barriers, and on evidence completeness below 1; with zero physical transitions the ratio is defined as 1 (`soak.go:69-74`).
`UBIQUITOUS_LANGUAGE.md` defines Verdict as "pass or fail"; the manifest lists as a known blind spot that no independent physical feedback is stored. `verify-run` only re-reads the files and checks digests and that the verdict matches them. Nothing in either command looks at episodes, situations or failures.

So: by design, not a defect against its spec. It is still a trap for this experiment: a run in which nothing happened is "pass", exactly as a run in which the right thing happened. The runbook already guards against it (pass needs one row in each table, `P0.5-RUNBOOK.md` section 6),
so the runbook criteria, not `verdict.json`, are the P0.5 pass test. Nothing to patch in P0.5.
Class: not a defect of the plumbing; design gap in the instrument-like part of Agentic Stream. Recommended action: P0.5 and later phases must never cite `verdict: pass` alone; add a liveness line to the P0.5 report (episodes, decisions, commands counts).
Owner decision needed: yes (whether `export-run` should emit `inconclusive` when an opened situation led to no decision, or add a `coverage` block; this touches a safety verdict, so it is the owner's call).

## F5. The 30 s budget against a reasoning model

Evidence. `zai/glm-5.3-flash` "always reasons" (`tamoz-agent-kernel/data/model_windows.yml:20-33`: 168 s and 8,300 reasoning tokens for a small task; request timeout pinned to 600 s). Reasoning tokens are counted in `output_tokens`.
Measured here at about 40 tokens/s: 1,348 tokens in 31.7 s (A), 2,397 in 56 s and 3,059 in 78.7 s (B). One call is therefore 30 to 80 s on a six-fact prompt. The spec's `wallTime: 30s` (spec line 250) cannot hold one call; `180s` held two calls and the validation with 45 s to spare.
The spec also allows `modelCalls: 5` (up to five calls, 300 to 400 s) and `outputTokens: 4000`, which two calls already exceed (5,456 used in B; B's `12000` was enough). Both are config in the spec's `cognition.executor.budget` (lines 249-258) and change the spec digest, so they are labelled changes in a new run folder, as the runbook says.
Class: our setup (September's 30 s fitted a stand-in; the runbook anticipated this risk). Action: set `wallTime: 300s` and `outputTokens: 20000` for the re-run, keep `modelCalls: 5`, `providerRetries: 2`.
Owner decision needed: no for the re-run. Yes later, for the real fan spec: what wall time the live experiment may spend on one decision (a 5 minute episode is slow against a thermal rise; a faster model or the non-reasoning variant is the alternative).
