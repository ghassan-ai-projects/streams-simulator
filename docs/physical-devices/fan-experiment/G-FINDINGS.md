- **`kind_digest`:** `"sha256:" + sha256(canonical(kind file))`. **`capability_digest`:** `SPEC.md:103-104` (array of `{kind, commands}` sorted by kind, commands by name, from `NBIRTH.kinds`). **Do not confuse it** with the firmware's `CAPABILITY_DIGEST` (`FW:35`, a device-wire catalog digest): different thing, same name.
- **Canonical JSON.** Needed: sorted keys (UTF-16 order; identical to code point order for the ASCII names here), no spaces, integers exact, strings unescaped except what JSON requires, `allow_nan=False`. Floats: an integral float must print as an integer (`45.0` becomes `45`), others as ES6 numbers (`1e-07` becomes `1e-7`). The kind files and `D7` arguments are integers; implement the float rule anyway (about 15 lines) and test it with vectors taken from the Go `canonical` package tests (UNVERIFIED which file holds them).
- **Validation.** `jsonschema` 4.25.1 is installed for the user's Python 3.9 (`~/Library/Python/3.9/...`), not declared anywhere. I ran `Draft202012Validator` over the vendored schemas: no `$ref` anywhere (self-contained); all 15 `valid` fixtures pass; every `invalid` fixture fails. Recommendation: **runtime stays stdlib** (hand-written strict validators for the five record types the gateway receives, `STATE NCMD DCMD DQUERY HSYNC`, like the existing device-wire validators); **`jsonschema` is a test-only dependency** that checks every record the gateway emits and runs all four fixture folders through both the schema and the hand validators (they must agree). Add a `requirements-dev.txt` beside the tools (the lab has none). The alternative, `jsonschema` at run time, adds a dependency the bench machine may not have (UNVERIFIED which Python the bench uses).

## 5. The board mapping (D7): what the gateway needs from it

`streamsim` defines the schema (S4); the gateway must not invent it. The gateway needs, for one board:

1. **Identity:** the plant wire `board` id and `environment: hardware`; the device ids with their kind and the firmware `target` for each (`led-01`, `fan-01`; none for the sensor); the firmware `device_id` (`board-01`, `FW:224`) to check frames against.
2. **Commands, kind to firmware:** `show_state {state}` to `set_led {brightness_permille, pattern}` (a table: `off` 0 / `off`, `watch` 500 / `slow_blink`, `alert` 1000 / `solid`, equal to the physical catalog presets, `arduino-mega-l293d-fan-led-capability-catalog.json` routes `set_indicator.presets`); `set_cooling {level_percent}` to `set_pwm_lease {duty_permille, lease_ms}` (a linear map, 45 % to 450 permille; `lease_ms` **not in the arguments any more**, so the mapping or the kind must give it, 5000 to 10000); `stop_led`, `stop_fan` to `safe_stop` with target. Each with its `expires_after_ms` cap (F3) and a statement that the mapped maximum (60 % = 600 permille) does not exceed the firmware's limit (`FW:17-19`), checked at load.
3. **Metrics, firmware to kind:** the temperature and humidity frames (`dht11-temperature`/`C` to `temperature`/`Cel`, `dht11-humidity`/`percent` to `humidity`/`%`) with the unit rename; `duty_permille` to `level_percent` (divide by 10); the LED `state` from brightness (500 and 1000 are distinct, so brightness alone inverts; 0 is `off`), with the shadow rule of F5 written down explicitly in the mapping, not guessed in code.
4. **Failure rules:** a raw value with no mapping entry is `suspect`; how long before a reading is `stale`.
5. **Preconditions and interlocks per command** (empty for this board), so the safe-stop start check has something to read.
6. **A digest** (RFC 8785 of the file) for logging now and announcing later (`PLAN.md:196-198`).

Until S4 lands, ship an in-repo mapping for the current 1.3.0 kinds that is nearly identity (`set_led` pattern code to name: `0` off, `1` slow_blink, `2` solid is UNVERIFIED; the kind says only "code 0 to 2" and the firmware accepts the three names, `FW:200-201`). Keep the translation behind one class (`BoardMapping`) so replacing it is one round.
