# Phase 3 review — typed application gateways

- **Scope:** feature gateway contracts, bridge adapter boundary, app workflow ownership, composition-root wiring, and production UI failure handling.
- **Outcome:** source boundary review found and closed three adapter-contract defects; **production-first validation remains pending**. The user-directed workflow defers test repair and full gates until the application migration is complete.

## Source review checklist

- Application stores use feature gateway capabilities rather than transport action strings and response parsing.
- Feature failures are closed by recovery meaning; diagnostic messages/codes are available for display only.
- Bridge adapters decode wire results to model/application values and do not absorb product workflow policy.
- Production app/UI source contains no legacy bridge failure/status/code/result branching or transport operation calls (the focused grep is recorded in [P3 evidence](../evidence/P3.md)).
- **Reviewed:** HTTP success payloads pass through nullable endpoint decoders; action responses require a `result` field; malformed advance/inject/end/destroy results fail decoding. Composition generation checks its required envelope fields before returning a typed value. `DomainDocument` is a non-indexable branded `object`. Feature failure mapping is in the bridge adapter and maps protocol codes/status to closed app failure kinds while retaining diagnostic display data.
- **Reviewed:** unsuccessful `run.verify` responses are recovered only when their embedded result passes the same replay decoder used for successful responses. Run-event records are decoded at the adapter edge before reaching the typed follower.
- **Disposition:** no blocking source-boundary finding remains. `destroyWorld` retains the prior best-effort cleanup behavior (`Promise<void>`); the adapter validates its result, while the app intentionally does not replace the original failure with cleanup failure.
