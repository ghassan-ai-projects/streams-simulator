# Phase 3 evidence — typed application gateways

- **Scope:** move protocol encoding/decoding to the bridge adapter and migrate application stores and UI decisions to feature-owned typed gateways and failure categories.
- **Outcome:** production-source migration is assembled; **validation is pending**. The user directed the team to complete production migration before repairing/rerunning legacy tests and gates. This record does not claim the Phase 3 exit.

## Delivered source shape

- `app/ports/` defines separate session, workspace, plant, editor, launch, and review gateways. Each operation returns a feature-owned `Outcome<T, Failure>`; diagnostic protocol codes remain display data rather than app decision branches.
- `adapters/bridge/` owns bridge request names, response decoding, report/playback decoding, and run-event decoding. `main.tsx` constructs the nested adapter set and injects feature gateways into application stores and route factories.
- App workflows remain app-owned. Plant creation still performs its file/existence, generation, write, and optional-composition sequence; the adapter exposes typed operations and does not take over that workflow.
- Production app/UI callsites use typed failure kinds and diagnostics. `rg -n 'BridgeFailure|\\.failure\\.(code|status)|\\.failure\\.result|action\\("|/api/' canvas/src/app canvas/src/ui --glob '!*.test.ts'` returned no matches.
- `model/launch.ts` owns the acknowledgement value consumed by launch policy; wire-field decoding stays at the adapter edge.
- P2's independently committed editor compose guard remains in `EditorStore`; its focused regression run is recorded in P2 evidence and is not a P3 validation claim.
